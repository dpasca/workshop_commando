# 03 · エディタの中のエージェント（45分）

**ゴール:** エディタがコーディングエージェントにマップの変更を依頼し、**何を受け入れるかはあなたが管理し続けます**。

これまではあなたがエージェントに話しかけ、エージェントがあなたのファイルを変更していました。今回は向きが逆になります。**あなたのプログラムがエージェントを部品として呼び出します**。
どのコーディングエージェントにもヘッドレスモード（`claude -p`、`codex exec`、`opencode run`）があり、プロンプトを受け取って回答を出力します。必要なのはそれだけです。

## 持ち帰ってほしい5つの考え方

1. **エージェントはステートレスな関数です。** レベルを渡し、レベルを受け取ります。状態（マップ、履歴、Undo）を持つのは*あなたのアプリ*です。エージェントの「セッション」には何も残りません。
2. **コンテキストはあなたが組み立てます。** プロンプトはコードで組み立てます。ルール、凡例、マップ、選択された行、直近のいくつかのリクエスト、新しいリクエスト。そのテンプレートを書くことで、エージェントが本当に必要とするものがわかります。
3. **最小権限。** エージェントにはツールもファイルも与えません。テキストで答えることしかできません。変更を適用するのはあなたのプログラムであり、決してエージェントではありません。
4. **出力を決して信用しないこと。** パースし、検証し、適用する前に表示します。ルールに違反した回答は適用せず、理由を添えて差し戻します（リトライ）。
5. **レイテンシは UX の問題です。** 回答には15〜45秒かかります。進捗を表示し、キャンセルできるようにし、ゲームを固まらせないでください。

## プロンプトの前に決めること

私たちのテストでは、エージェント単独でこのゴールに約15分で到達しました。時間は判断に使ってください。

1. **回答の形式。** 「選択範囲の行を、行番号付きで完全な形で返す」とすると、回答が小さくチェックしやすくなります。
2. **何を変更してよいか。** どの行か、どのグリッドか。エージェントが敵の定義に触れることを許可する場合はあるか。
3. **考えている間の編集。** 回答には15〜45秒かかります。最も単純なルールは、承認（Accept）か却下（Reject）をするまで描画を止めることです。
4. **ルールをどこに置くか。** プレイヤーの開始位置と、何を歩行可能とみなすかは、現在 `GameScene.ts` の内部にしかありません。共有モジュールに移し、ゲームとチェッカーの判断が一致するようにしてください。

## 手順（まずゴールまで）

1. **dev サーバーから CLI を呼び出し**、固定のプロンプトで返ってきた内容を出力します（下の表を使ってください）。
2. レベルから**プロンプトを組み立てます**。指示、凡例、マップ、リクエスト。パースできる形式での回答を求めてください。
3. 回答を**パースして検証します**。行数が正しいこと、セルが2文字であること、既知のコードだけであること、そして**ゲームプレイのチェックを1つ: 下端から上端まで歩行可能な経路がまだあること**。下のリストの残りは発展課題です。
4. **プレビューして適用します。** 提案された変更をマップ上に表示します。承認で適用し（Undo 可能）、却下で破棄します。その後はいつも通り Save します。

## CLI をヘッドレスで呼び出す

それぞれ**空の一時フォルダ**で実行します。Claude はツールをオフにし、Codex は読み取り専用のサンドボックスで実行します。どちらの場合もエージェントには読むものも書く場所もないので、できるのは回答することだけです。
以下の形はそのままテスト済みです。プロンプトは最後の引数です（または stdin、下記参照）。CLI はモデルが書いたものをそのまま返すので、**プロンプトで回答形式を厳密に指定し**、パーサーは前後の余計な文章を許容するようにしてください。

| ツール | コマンド | 回答の場所 |
|---|---|---|
| Claude Code | `claude -p "<prompt>" --tools "" --no-session-persistence --output-format text --setting-sources "" --disable-slash-commands` | stdout |
| Codex | `codex exec --sandbox read-only --skip-git-repo-check --ephemeral --ignore-user-config -C <tmpdir> -o <tmpdir>/out.txt "<prompt>"` | `-o` に指定したファイル |
| OpenCode | `opencode run --pure --dir <tmpdir> --format json "<prompt>"` | JSON Lines。`type: "text"` のイベントの `part.text` を連結します |

品質と引き換えに速度を上げるには `--model sonnet`（Claude）または `-m <model>`（Codex、OpenCode）を追加します。私たちのテストでは、Claude の `sonnet` は10〜19秒で回答し、デフォルトでは約40秒でした。
プロンプトは引数ではなく**stdin で渡してください**。プロンプトは10〜15 KB になります。`claude -p` はプロンプトが指定されていないと stdin を読みます。Codex ではプロンプトとして `-` を使います（`codex exec ... -`）。どちらもテスト済みです。Windows でのクォートの問題も避けられます。
OpenCode の出力形式はドキュメントをもとに書いたもので、実際にログインした状態ではまだ試していません。違っていたら、目の前の結果を信じてください。

注意点: ユーザーがキャンセルしたら子プロセスを kill する · タイムアウトを設定する · Windows ではコマンドが `.cmd` のシムなので、シェル経由で起動する（そしてプロンプトは stdin で渡す）。

## プロンプトに入れるもの

役割 · ゲームの3文での説明 · マップの形式 · 凡例（と各敵の動きを言葉で） · 結果が守るべきルール · コンテキストとしてのマップ全体 ·
**変更してよい行** · 最近のリクエストとそれをどう扱ったか（発展課題） · リクエスト · 正確な回答形式。逃げ道も用意します:
*「ゲームにできないことが必要な場合は、代わりに `NEEDS: <what>` と答えてください」*。次に何を作るべきかを知る最も安上がりな方法です。

## 何を検証するか

行数とセル数が正しい · 既知のコードだけ · **下端から上端まで歩行可能な経路がまだある** · ユニットは歩行可能なセルの上にある ·
戦車の4セルがすべて道路上にある · プレイヤーの開始位置から4タイル以内に何もない · アイテムに到達できる。（チェッカーを書きましょう。エージェントにも書けます。）
エージェントの責任にするのは、*その変更*が持ち込んだ問題だけにしてください。

全員のチェッカーの判断が一致するための定義: 歩行可能 = `..`、`rd`、`==` · それ以外はすべて通行不可（樽と木箱は撃って壊せますが、通行不可として扱います） ·
プレイヤーは下端中央から開始します: 最後から2番目の行、列7と8。

## 完了条件

- [ ] 「2人のスナイパーが守る橋を追加して」と入力すると、マップ上に提案が表示される
- [ ] 承認で適用され（Undo で元に戻せる）、Save でファイルに書き込まれ、ゲームがそれを読み込み直す
- [ ] ルールに違反する回答を出させることができ、それが理由付きで却下される。
  良いモデルはプロンプトにルールがあればめったに違反しないので、強制的に起こしてください。プロンプトからルールを外し（チェックボックスがあると便利です）、
  「マップ全体を横切る壁」を依頼するか、手書きの不正な回答をパーサーに貼り付けます。

## 発展課題

問題をフィードバックしてリトライする · 行範囲に制限する · 次のプロンプトに渡す履歴リスト · モデルの選択 ·
`NEEDS` の回答を、コーディングセッションで作業の起点にできるファイルに記録する · 同じリクエストを2つのモデルで試して比較する。

## または: 完成版を使う

完成版に切り替え（`git worktree add ../commando-exercise-3 exercise-3`）、次のことを行います。

1. リクエストを5つ試します。妥当なものを3つ、曖昧なものを1つ（「もっと良くして」）、不可能なものを1つ（「ヘリコプターのボスを追加して」）。
2. 同じリクエストを2つのモデルで試します（例えば `sonnet` とデフォルト）。時間、結果、それぞれがどれだけ形式に従ったかを比較します。
3. **壊して**みます。受け入れるべきでないのに受け入れてしまうものは何か。チェッカーが見逃すものは何か。発見を3つ書き出してください。
4. `data/requests.md` と `data/ask_log.jsonl` を開きます（完成版が書き出します）。そこから次に何を作りますか。

## 仕上げ: レベルを選ぶ

最後のセッションで見せるベストなレベルを選んでください。自分のノートPCでもプロジェクターでも構いません。うまくいったリクエストと、うまくいかなかったリクエストを1つずつ添えてください。
